# 部屋のサーバーの中の動き

部屋のサーバー（Cloudflare版とVercel版）が、中でどう動いているかを説明します。
部屋のサーバーを直したい人や、ふるまいの理由を知りたい人に向けたページです。
置くだけなら、[サーバー版のしくみ](https://xelltis.github.io/udonarium_axe_backend/server/)を読めば足ります。

## 全体の形

```text
Axe（参加者ごと）
 │  POST /v1/rooms          … 部屋を作る
 │  GET  /v1/rooms          … 部屋の一覧
 │  GET  /v1/rooms/<鍵>     … 部屋を鍵で1つ引く
 │  DELETE /v1/rooms/<鍵>   … 部屋を削除する（GMだけ）
 │  GET  /v1/rooms/<鍵>/ws  … 部屋に入る（WebSocket）
 └─ HEAD・GET・PUT /v1/rooms/<鍵>/assets/<SHA-256>
                            … 部屋のアセット（画像と音声）
        │
        ▼
部屋のサーバー
 ├─ 部屋ごとの卓の状態 … Cloudflare版は部屋ごとのDurable Object（SQLite）、Vercel版はRedis
 ├─ 部屋の一覧         … Cloudflare版はロビーのDurable Object、Vercel版はRedis
 └─ 部屋のアセット     … Cloudflare版はR2、Vercel版はVercel Blob。名前は rooms/<鍵>/<SHA-256>
```

1. 部屋を作ると、部屋のサーバーが128ビットの乱数で**部屋の鍵**（`roomKey`）を決めます。表示用の3文字のID（`roomId`）も付けます。
2. 参加者は、部屋の鍵のURLにWebSocketでつなぎ、最初に`hello`を送ります。パスワードのある部屋なら、ここでサーバーが照らします。
3. 入れたら、サーバーは部屋にいる人の一覧と、自分が持っているオブジェクトの一覧（カタログ）を送ります。
4. あとは、参加者が送ったイベントを、ほかの参加者へ中継します。

## 卓の同期

### サーバーは「全部を持っているピア」

Axeは、卓のオブジェクトを参加者どうしで見せ合い（カタログの交換）、足りないものを取り寄せて同期しています。
部屋のサーバーは、この仕組みに**もう1人のピア**（`@authority`）として加わります。
カタログの交換はこのピアとだけ行うので、参加者が増えても交換の回数は増えません。

- 入ってきた人がサーバーより新しいものを持っていれば、サーバーが取り寄せます。
- サーバーの方が新しいものは、入ってきた人がサーバーから取り寄せます。
- 消したオブジェクトを持っていれば、サーバーが消させます。

### 新しい方を勝たせる

オブジェクトを書き換えるイベント（`UPDATE_GAME_OBJECT`）は、サーバーが持っているものと版を比べてから配ります。
版は、書き換えた回数と、0以上1未満の乱数の和です。Axeが参加者どうしで比べるのと同じ決まりです。

| 届いた版                 | サーバーがすること                     |
| ------------------------ | -------------------------------------- |
| 持っているものより新しい | 置き換えて、ほかの全員に配る           |
| 持っているものと同じ     | 何もしない                             |
| 持っているものより古い   | 配らず、持っている方を送り主に送り返す |
| 消したオブジェクト       | 配らず、送り主に消させる               |

伏せた形で持っている人が古い版で書いてきたときは、置いてある方を`AUTHORITATIVE_OBJECT`で返します（→ [見せないもの](./protocol.md#見せないもの)）。

版を一度に大きく上げる書き込みは受けません。1回の書き込みで上げてよい回数は2の20乗までで、初めて置くものの回数も2の20乗までです。上限（2の50乗）まで上げて、だれにも書き換えられなくすることを防ぐためです。0より小さい回数と、-1から1の外の乱数も受けません。Axeが書くたびに1ずつ上げる版は、これに当たりません。

消したオブジェクトには、その印（tombstone）を残します。
印があるあいだは、つなぎ直した人が古い写しを持っていても、消したものは生き返りません。
印は1つの部屋に10万件までで、超えたら古いものから8万件まで減らします。印を減らしたものは、古い写しを持つ人がつなぎ直すと戻ることがあります。
印を残すかは、送られてきた種類名ではなく、置いてあるものの種類で決めます（カーソルには残しません）。
部屋を読み込み直すときのように、消したものを同じ名前で戻したいときは、Axeが先に「戻す」と知らせ（`FORGET_DELETED_OBJECTS`）、サーバーも印を外します。

### カーソルは、その人がいるあいだだけ

参加者ごとのカーソル（`PeerCursor`）は、その人が部屋にいるあいだだけ持ちます。
カーソルを書いたり消したりできるのは、その人の席だけです。サーバーは、カーソルのピアID・ユーザーID・役割を席の値にして置きます。
その人が抜けると、サーバーは持っていたカーソルを消し、ほかの参加者には「抜けた」とだけ知らせます。
カーソルには消した印を残さないので、同じ人が入り直せば、またカーソルを出せます。

部屋のサーバーが落ちると、出ていく知らせが届かないまま、その人のカーソルが残ります。
そうしたカーソルは、だれかが入ってきたときと、見回りのときに消し、ほかの参加者にも消させます。

### 同じ人が2本つないだら

同じ人が同じピアIDで新しくつないだら、古い方を閉じます（`replaced`）。
回線が切れたのにサーバーがまだ気づいていない接続が、幽霊のように残らないためです。
SkyWay版では、こうした接続が60秒ほど残ることがありました。
古い接続のカーソルは、すぐには消しません。同じページがつなぎ直したときは、同じカーソルで戻るためです。読み直したページや別のタブは別の識別子のカーソルを書くので、そのときに古い方を消して、ほかの参加者にも消させます。

同じ人かどうかは、ユーザーIDとログインの有無で見ます。
ほかの人のピアIDを名乗る接続は、`bad-message`で断ります。
入れると、その人を追い出して成り代われてしまうからです。
ただし、ログインした人のピアIDを見学が先に取っていたら、その人が入ってきたときに見学のほうを外します。
ピアIDはユーザーIDから作るので、ログインした人のピアIDを持てるのはその人だけだからです。

## 卓の状態の置き場所

### Cloudflare版

部屋のDurable Objectは、卓の状態をSQLiteに置きます。

- しばらくやりとりが無いと、Durable Objectは眠り（Hibernation）、メモリの中身は消えます。接続は切れず、次のメッセージで起き直します。そのため、接続中でも状態はSQLiteに書いています。
- 書き込みは、オブジェクトごとに1秒ぶんまとめてから書きます。コマをドラッグして何十回も書き換えても、書くのは1回で済みます。落ちたときに失うのは最大で1秒ぶんです。追加と変更はつなぎ直したときのカタログの交換で戻りますが、削除は戻らず、消した物がまた現れます。消した物を戻した知らせ（`FORGET_DELETED_OBJECTS`）も失われるので、そのあいだに戻した物はまた消えます。
- オブジェクトは、約8KiBずつページ（`pages`の1行）にまとめて置きます。Cloudflareは、SQLiteが読み書きした行の数で数えます。オブジェクトごとに1行にするより、部屋を読み込むときに書く行も、起き直すときに読む行も少なくて済みます。1行には、オブジェクトの索引（1つを1行のJSONにしたもの）と、中身（MessagePack）をつないだものを置きます。
- 書き込みでは、変わったオブジェクトのあるページだけを丸ごと書き直します。入らなくなったオブジェクトは最後のページへ移し、空になったページは消します。
- 4KiBを超えるオブジェクトは、ページではなく`blobs`に置き、1MiBずつ行を分けます（SQLiteの1行は2MBまで）。大きな白板を書き換えても、ほかのオブジェクトのページは書き直しません。
- 消した印は、`marks`の1行に1,000個ずつ、古い順に置きます。
- 起き直したときは、ページの索引だけを読みます。中身は要るときにページごとに読み、16MBまでメモリに持ちます。
- 1回の書き込みは、1つのトランザクションにします。書けないものがあると全体を戻し、オブジェクトを1つずつ書き直して、書けないものだけを捨て、索引をSQLiteにあるとおりに戻します。
- ページより前に作った部屋（`objects`のテーブルがある部屋）は、作ったときのまま、オブジェクトごとに1行で置きます。ページに詰め直すと、最初に開いた人を起き直しの3倍ほど待たせるためです。保持期間で消えるのを待ち、この置きかた（`src/rooms/legacy-store.ts`）は次のリリースで消します。

### Vercel版

Vercel版は、卓の状態をRedisに置きます。

- 部屋のWebSocketを受けたインスタンスのうち1つが、Redisで部屋の貸し出し（lease、15秒。5秒ごとに延ばす）を取って、その部屋を受け持ちます。受け持つインスタンスは、卓の状態をメモリに持ち、Redisに書きます。
- ほかのインスタンスに着いたWebSocketは、RedisのPub/Subで、受け持つインスタンスへ中継します。
- 受け持つインスタンスが替わると、部屋のサーバーは接続を`moved`で閉じ、Axeは静かにつなぎ直します。WebSocketは、Functionの最大実行時間より前に`rotate`で閉じます（→ [別の接続でつなぎ直してもらう](./protocol.md#別の接続でつなぎ直してもらう)）。中継しているWebSocketは、送ってきたものが受け持ちに届いてから閉じます。
- 受け持つインスタンスは、自分に直接つながったWebSocketが無くなると、部屋を手放します（`rotate`で閉じたものは、つなぎ直しを15秒待ってから）。Vercelは呼び出しの無いインスタンスを止めることがあり、中継だけでは受け持ちを続けられないためです。そのため、直接つないでいた最後の人が`rotate`で別のインスタンスにつなぎ直したときも、受け持ちは替わります。手放す前に書き残しをRedisに書くので、卓の状態は失いません。部屋のサーバーがメモリにだけ持つもの（PLが消せなかったタブの行を守る20秒、送り主に返した物の記録、ダイスの順番待ちなど）は、新しい受け持ちでは初めからになります。
- 消す時間が過ぎた部屋は、部屋の一覧・作る・入るのついでと、1日1回のVercel Cron（`/internal/sweep`）で消します。

### 見回り

人がいるあいだは、ときどき部屋を見回り、実際につながっている人を数え直します（Cloudflare版は1時間ごと、Vercel版は30秒ごと）。
部屋のサーバーが落ちると、出ていく知らせが届かないまま接続が切れます。そのときも、一覧の人数を直し、そこから保持期間を数えて消します。

ログインした席のトークンが切れて1分を過ぎたときも、見回りでその席を外します（→ [`auth`](./protocol.md#auth)）。
3時間`active`が届かない席（ページが放っておかれた席）も、見回りで外します（→ [`active`](./protocol.md#active)）。
見回りの時刻は、部屋でいちばん早く切れるトークンや、いちばん早く3時間を過ぎる席に合わせて早めることがあります。
席がトークンを渡し直したときは、見回りの時刻も新しいトークンに合わせて延ばします。Cloudflare版では、延ばさないとアラームが古い期限のまま起き、眠っていた部屋が索引を読み直すだけで終わるためです。
外れて部屋が空になれば、ふつうに出ていったときと同じく、そこから保持期間を数えます。

## 見え方を決める決まり

どれを誰に届けないかは、[サーバー版のしくみ](https://xelltis.github.io/udonarium_axe_backend/server/#見えない情報)にあります。ここでは、その決まりを守るためのふるまいを書きます。

見え方はユーザーIDで決まります。
見学者（ログインしていない人）は、ログインした人のユーザーID（`acct_`で始まるもの）と、この部屋にログインして入ったことのあるユーザーIDを名乗れません。そのため、ログインした人のカーソルに見えるユーザーIDを名乗って、その人の手札や秘話をのぞくことはできません。ただし、ログインしていない見学者のユーザーIDと、SkyWay版の卓を読み込んだ部屋に残るユーザーIDは、どちらにも当たらないので名乗れます（→ [安全のしくみ](https://xelltis.github.io/udonarium_axe_backend/operate/security#守っていないこと)）。

部屋の読み込みや複製では、子が親より先に届くことがあります。
親がまだ届いていないものは、見え方を決められないので、だれにも配りません。親が届いてから見え方を確かめ、見てよい人に渡します。

GMでない人は、書き込みで自分に見えるものを増やせません。
データ要素の名前を変えたり、ものを別の親の下に移したり、まだ無い親の下へ移してからその親を作ったりして伏せたものを手に入れることも、発言の送り主を変えることも、ほかの人の手札にあるカードの向きや持ち主を変えることも、カードをほかの人のものにすることも、持ち主でない人が、メモの公開範囲や、持ち主のいるメモ・ダイスの持ち主を変えることも、山札の中のカードに持ち主を付けることも、山札の中のカードを手札の印で自分のものにすることも、持ち主や手札の印の付いたカードを山札に入れることも、自分の発言でないものの宛先を変えたりシークレットを外したりすることも、読めないメモを自分のものにすることも、タブをPLや見学者に見せるかを変えることもできません。
ほかの人の手札のカードは、伏せたまま自分の手札へ引くこと（Axeの「相手の手札から引く」）だけができます。

カードをめくったり手札に入れたり、秘話の宛先を変えたり、役割が変わったりして見え方が変わると、見えるようになった人に渡し、見えなくなった人の手元から外させます。
細かい決まりは[部屋のプロトコル](./protocol.md#見せないもの)にあります。

## ログイン

### ログインの流れ

Axeは、ログインのために次のことをします。

```text
Axe                         部屋のサーバー                  Discord
 │ code_verifier を作る
 │ ── ページを開く ──────────▶ GET /v1/login/discord
 │                             │ ── 同意の画面へ ───────────▶
 │                             │ ◀── 戻る（コード）──────────
 │                             │ GET /v1/login/discord/callback
 │                             │ （Discordで、その人のIDと名前を1度だけ読む）
 │ ◀── 戻り先#login_code=… ──
 │ POST /v1/auth/token（コード＋code_verifier）
 │ ◀── アクセストークンとリフレッシュトークン
```

1. Axeは乱数の`code_verifier`を作って手元に置き、そのSHA-256（`code_challenge`）と戻り先のURLを付けて、`/v1/login/discord`をページとして開きます。
2. 部屋のサーバーは、Discordの同意の画面へ送ります。求めるのは`identify`（その人のIDと名前とアバター）だけで、メールアドレスや参加しているサーバーは求めません。
3. Discordから戻ってくると、部屋のサーバーはDiscordでその人の情報を1度だけ読み、使い捨てのコードを付けて、Axeの戻り先へ返します（`#login_code=…`）。
4. Axeは、そのコードと`code_verifier`を`POST /v1/auth/token`に送り、トークンの組を受け取ります。

コードはURLのフラグメント（`#`のあと）に付くので、サーバーのログやほかのサイトへの`Referer`には残りません。
コードを横取りされても、`code_verifier`を持っていないと使えません（PKCE）。
Discordのアクセストークンは部屋のサーバーのどこにも置かず、その人の情報を読んだらそれきりです。

### 戻り先

戻り先は、`ACCESS_CONTROL_ALLOW_ORIGIN`に**名前で書いた**Originのページだけです。
`*`と書いていても、ログインの戻り先には数えません。
どこにでも戻せると、ほかのサイトがログインのコードを受け取れてしまうためです。

### トークン

| もの                     | 使えるあいだ | 使いかた                                                              |
| ------------------------ | ------------ | --------------------------------------------------------------------- |
| アクセストークン         | 15分         | 部屋の`hello`と、`Authorization: Bearer`                              |
| リフレッシュトークン     | 30日         | アクセストークンが切れる前に、`POST /v1/auth/token`で新しい組に替える |
| 部屋のアセットのトークン | 15分         | 部屋のアセットの`Authorization: Bearer`。部屋のサーバーが席に渡す     |
| ログインのコード         | 5分          | 1度だけ。`POST /v1/auth/token`でトークンの組に替える                  |
| ログインの途中           | 10分         | `/v1/login/discord`を開いてからDiscordから戻るまで                    |

- リフレッシュトークンは、使うたびに新しいものに替わり、使ったものはもう使えません。
- 使ったリフレッシュトークンがまた来たら、盗まれたとみなし、その系統のトークンをすべて無効にします。持ち主もログインし直すことになります。同じものが同時に2回来ても、通るのは1回だけで、2回目で系統ごと無効にします。
- アクセストークンは、部屋のサーバーが`SESSION_SECRET`で署名したJWT（HS256）です。部屋のサーバーのどこにも置かず、署名と期限で確かめます。

## 役割を変える

GMは、部屋にいる人の役割を変えられます。
Axeは、サーバー（`@authority`）に`ROLE_REQUEST`を送ります。

```json
{ "eventName": "ROLE_REQUEST", "data": { "peerId": "Zz9Yy8XyZq9W8e7r6-", "role": "gm" } }
```

変えたら、その人の`PeerCursor`の役割を書き換えて版を上げ、全員に配ります。
その人には、新しい役割の部屋のアセットのトークンも`asset-token`で送ります。`asset-token`の`role`に新しい役割が入るので、Axeはこれで自分の役割を知り直します。
断るときは、頼んだ人に`ROLE_REJECTED`を返します。

| `reason`           | 起きるとき                       |
| ------------------ | -------------------------------- |
| `not-game-master`  | 頼んだ人がGMでない               |
| `unknown-peer`     | その人が部屋にいない             |
| `not-logged-in`    | ログインしていない人は見学のまま |
| `last-game-master` | 部屋のGMがいなくなる             |

GMの数には、部屋の席の表にGMとして残っている人をすべて数えます。いま部屋にいないGMと、アカウントを消したGMも入ります。
そのため、ほかのGMがアカウントを消していると、自分をPLにする変更は断られず、部屋に入れるGMがいなくなります。

## 招待

GMは、役割の付いた招待を作れます。
Axeは`{"type":"invite","role":"pl"}`を送り、返ってきた`invite`を招待リンクに載せます。

- 招待は、作ってから30日使えます。
- 30日を過ぎた招待や、`SESSION_SECRET`を替える前の招待は、断られずに無いものとして扱われます。ログインした人は初めて入るときにPLになり、そのロールが覚えられます。あとから新しい招待を渡しても変わらないので、GMが部屋で`ROLE_REQUEST`を送って変えます。
- 招待で決まるのは、ログインした人がその部屋に**初めて**入るときの役割です。前に入ったことのある人は、今の役割のままです。
- 役割を覚えるのは、席に着けたときだけです。`room-full`などで断られたときは何も覚えないので、次に入るときにもその招待が効きます。
- ログインしていない人は、招待があっても見学です。
- ほかの部屋の招待は使えません。
- GMの招待は、出した人がもうGMでなければ効かず、PLとして入ります。GMを外された人が前に配ったリンクで、GMを増やせないようにするためです。PLと見学の招待はそのまま効きます。
- アカウントを消しても、部屋の席の表にはGMのまま残るので、その人が出したGMの招待は、作ってから30日のあいだ効き続けます。

## 運営する人の管理画面とBAN

`ADMIN_DISCORD_IDS`を入れた部屋のサーバーは、`/admin`に管理画面を、`/admin/api`にそのAPIを持ちます（`src/core/http/routes/admin.ts`）。
置く人に向けた使いかたは[管理画面とBAN](https://xelltis.github.io/udonarium_axe_backend/operate/admin)にあり、ここでは中の動きを書きます。

### 画面

画面は1枚のHTMLで、スタイルとスクリプトを中に持ちます（`src/core/admin/page.ts`）。
答えるたびにnonceを作り、`Content-Security-Policy`でそのnonceの付いたスタイルとスクリプトだけを動かします。
部屋の名前やDiscordの表示名はだれでも決められるので、スクリプトはどれも`textContent`で入れ、HTMLとしては入れません。
ログインはHttpOnlyのcookieにあり、スクリプトは読みません。APIを呼ぶときは`X-Admin-Request: 1`を付けます。
スクリプトはテストで動かさないので、画面を変えたら、手元のサーバー（`npm run serve`）をブラウザで開いて確かめてください。

### ログインとパスキー

管理画面に入るには、Discordとパスキーの2つを通ります（`src/core/http/routes/admin-auth.ts`）。

1. `GET /admin/login`が、Discordへ送ります。戻り先は`/admin/login/callback`で、`state`には署名した乱数（`admin-login`）を入れ、同じ乱数をcookie（`SameSite=Lax`）にも置きます。戻ってきた`state`とcookieが合わなければ断ります。ほかのサイトが、自分のログインをこのブラウザに差し込めないようにするためです。
2. Discordの答えのIDが`ADMIN_DISCORD_IDS`にあり、`mfa_enabled`（2段階認証）が有効なら、ログインのcookieを`stage: discord`で作ります。この段では、パスキーを確かめる（無ければ1つ目を登録する）ことしかできず、10分で切れます。
3. パスキーで確かめると、`stage: passkey`になり、ほかのAPIを使えます。

ログインのcookie（`src/core/http/admin-session.ts`）は、`SESSION_SECRET`で署名したトークン（`admin`）です。HTTPSでは`__Host-axe-admin`、`HttpOnly`・`Secure`・`SameSite=Strict`にします。
APIを呼ぶたびに、次を確かめます。

- `X-Admin-Request: 1`が付き、`Origin`があれば管理画面のものであること（`fromDashboard`）。フォームやほかのサイトのページは、どちらも満たせません。
- トークンが有効で、`sub`がいまも`ADMIN_DISCORD_IDS`にあり、`epoch`が置き場所の世代（`adminEpoch`）と同じこと。「すべての人をログアウトさせる」は世代を上げるので、それより前のログインはすべて通らなくなります。
- そのログイン（`sid`）でログアウトしていないこと（`sessionEnded`）。ログアウトすると、置き場所がその`sid`を、ログインが長くても切れる12時間後まで覚えます。ログアウトの前に出した呼び出しの答えは、Cookieを付け直して届きます。そのCookieでログインが戻らないようにするためです。
- `stage: passkey`のログインは、呼ぶたびに切れる時刻を30分先へ延ばします。ただし、Discordでログインしてから12時間（`SESSION_MAX_SECONDS`）を超えません。
- 部屋の削除、パスキーの削除、すべての人をログアウトさせることは、パスキーで確かめた時刻（`verified`）から5分（`STEP_UP_SECONDS`）以内に限ります。過ぎていれば`403 reauth-required`を返し、ページがパスキーで確かめ直してから呼び直します。

パスキー（`src/core/admin/webauthn.ts`）は、ES256とRS256だけを受けます。
作るときは、ブラウザが`getPublicKey()`で渡す公開鍵（SubjectPublicKeyInfo）を置き、attestationは求めません（`none`）。
COSEの鍵を読まないので、CBORは扱いません。
確かめるときは、`clientDataJSON`の種類・チャレンジ・Origin、`authenticatorData`のサイト（RP ID、管理画面のホスト名）のハッシュ、ユーザーの確認（UP・UV）、署名を確かめます。
署名の数（signCount）を数える認証器で、数が増えていなければ、写された認証器かもしれないので断ります。
チャレンジは、ログインの`sid`と目的（登録か確かめか）を入れて署名したトークンで渡し、答えに使えるのは1度だけです（`takeChallenge`。Cloudflare版は`challenges`の表、Vercel版は`mod:challenge:<値>`を`NX`で置く）。

最初のパスキーは、`stage: discord`のログインで、そのIDにパスキーが1つも無いときだけ登録できます。
2つ目からは、パスキーで最近確かめたログインでだけ登録できます。
`ADMIN_PASSKEY_RESET`にあるIDは、パスキーがあっても`stage: discord`で登録できます（すべての端末を失くしたとき）。
パスキーは1人10個まで、最後の1つは消せません。

ログインと、断った試み（`denied <理由>`）は、記録に`admin`として、運営する人のDiscordのアカウント付きで残します。
テストでは、ソフトウェアで作った認証器（`test/shared/passkey-helpers.ts`）でパスキーを作り、署名します。

### BANを確かめるところ

| BAN        | 確かめるところ                                                                                 | 読むBAN  | 断りかた                                               |
| ---------- | ---------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------ |
| IPアドレス | `/v1/rooms`・`/v1/auth`・`/v1/account`の下（Originを確かめたあと、`banGuard`）                 | 写し     | `403 banned`                                           |
| IPアドレス | ログインを始めるときと、Discordから戻ったとき（回数の上限を確かめる前）                        | 写し     | 戻り先に`login_error=banned`                           |
| どちらも   | Discordから戻ったとき（その人の情報を読んだあと、アカウントに書く前）                          | 読み直す | 戻り先に`login_error=banned`                           |
| Discord    | `POST /v1/auth/token`（アカウントに尋ねる前）                                                  | 写し     | `400 invalid-grant`（Axeはログアウトする）             |
| どちらも   | `POST /v1/auth/token`（アカウントがコードかリフレッシュトークンを正しいと認めたあと）          | 読み直す | IPアドレスは`403 banned`、Discordは`400 invalid-grant` |
| どちらも   | 部屋を作るとき（アクセストークンと回数の上限を確かめたあと。Discordはアクセストークンの`sub`） | 読み直す | `403 banned`                                           |
| Discord    | 部屋のアセットの読み書き（部屋のアセットのトークンの`sub`）                                    | 写し     | `403 banned`                                           |
| どちらも   | 部屋の`hello`（席に着く前と、着いたあとにもう一度）                                            | 読み直す | `banned`で閉じる                                       |
| どちらも   | BANしたときに部屋に入っている席（人のいる部屋をすべて回る）                                    | —        | `banned`で閉じる                                       |

Discordのアカウントを止めたとき、トークンの更新で`banned`を返さないのは、Axeが`invalid-grant`のときだけログアウトし、ほかのコードではログインを残したままにするためです。
席は`banned`で閉じます。Axeはつなぎ直さず、BANされていることを出します。
`banned`を知らない古いAxeは、知らない理由として3回までつなぎ直してから止まります。
どちらも、やりとりの形を変えないので、`PROTOCOL_VERSION`は上げていません。

### 部屋の`hello`とBAN

部屋は、`hello`が来るたびにBANを置き場所から読み直し（`RoomHost.bans`）、読めてから`hello`を確かめます。
BANしたアカウントは、まだ切れていないアクセストークンを持っていても、これで入れなくなります。
`hello`そのものは、同じ接続のほかのメッセージが割り込まないよう同期で確かめるので、BANを読むのはその手前です。
読むあいだに同じ接続に届いたものは、`hello`を確かめたあとに、届いた順で受けます。
Axeは入るまでほかに何も送らないので、`MAX_WAITING_FRAMES`を超えて届けば`too-many-messages`で閉じます。
送信元のBANは、部屋のこと（パスワードなど）を確かめる前に、アカウントのBANは、アクセストークンを読んだところで確かめます。

BANを読むあいだにBANされた人は、その前のBANで席に着いてしまいます。
BANしたときに席を閉じるのは人のいる部屋だけなので、その部屋がまだ一覧で0人なら、席は残ります。
そこで、席に着いたら、部屋の一覧に知らせ終わるのを待ち（`RoomHost.listed`）、BANをもう一度読みます。
このBANがBANより後に読んだものなら、ここで閉じます。
先に読んだものなら、BANが部屋を回るときには一覧に人数が載っているので、そちらが閉じます。

BANをすぐに返すホスト（テストの`FakeHost`）では、`hello`は待たずに確かめ、2度目は読みません。

### BANの置き場所と、インスタンスごとの写し

BANと記録は、Cloudflare版は`ModerationDurableObject`（Workerに1つ、名前は`moderation`）のSQLiteに、Vercel版はRedis（`mod:bans`と`mod:activity`）に置きます。

各インスタンスは、読んだBANの写しを`BAN_CACHE_MS`（30秒）のあいだ使います（`Moderation.current`）。
`banGuard`をはじめ、たいていの確かめはこの写しで行い、置き場所は読みません。
BANを変えたインスタンスは写しを捨てて、次のリクエストで読み直します。

ほかのインスタンスでもBANがすぐ効くよう、通すと費用につながるところ（部屋に入る、部屋を作る、ログイン、トークンを出す）では、BANを置き場所から読み直します（`Moderation.fresh`。上の表の「読み直す」）。
読み直すのは、そのリクエストが答えるに値すると分かってから、つまり正しいトークンやログインがあり、送信元ごとの回数の上限の内にあるときだけです。
置き場所を読むのは1回ごとに費用がかかるので、BANした送信元やでたらめなリクエストに大量に呼ばれても、読む回数が回数の上限を超えて増えないようにするためです。
1つのリクエストで何度確かめても、読むのは1度です。読み直したBANは、そのまま写しにもなります。

- 部屋の`hello`は、部屋ごとに読み直します（Cloudflare版は部屋のDurable Objectから`ModerationDurableObject`へ、Vercel版は受け持つインスタンスからRedisへ）。WebSocketを開くリクエストが回数の上限（`room`）を通ったあとなので、読む回数はその上限の内に収まります。
- アセットを置くのは、写しで確かめます。置けるのはいま席に着いている人だけ（`canUpload`）で、BANはその人の席をすぐに閉じ、入り直させないので、置き場所を読まなくても、すぐに止まります。
- 部屋の一覧、部屋のアセットを読む、部屋を削除する、アカウント、ログインを始める、は、写しだけで確かめます。ほかのインスタンスでは最大30秒遅れますが、通しても費用につながりません。

Cloudflare版では、あるリクエストが始めた読み込みを、ほかのリクエストが待つことはできません（Workerの決まり）。
そのため、写しが古いときは、気づいたリクエストがそれぞれ読み直します。
読み込みが重なったときは、後に始めた読み込みの結果を写しにします。
読めなかったときは、それまでの写しを使い続け、30秒たってからまた読みます。置き場所が答えないだけで、すべてのリクエストを止めないためです。
読み直すはずのリクエストと`hello`も、読めなければそれまでの写しで確かめます。

### 回数の上限を締める

運営する人が上限を締めると（`Tighten`、上限ごとに1・2・4・10）、1つのリクエストをその回数として数えます（`notingLimits`）。Cloudflare版の上限は`wrangler.jsonc`の`ratelimits`で決まっていて動かせないので、バインディングの`limit`をその回数だけ呼びます。Vercel版は`INCRBY`でその数だけ足します。
締めた具合は止めているもの・BANと一緒に読み（`ModerationStore.state`、Cloudflare版は`admin_state`の`tighten_*`、Vercel版は`mod:tighten`）、各インスタンスの写し（`BAN_CACHE_MS`）で見ます。リクエストごとに置き場所を読まないので、締めても費用は増えません。ほかのインスタンスには最大30秒遅れて効きます。

### 緊急停止

止めているもの（`Pause`）は、BANと同じ置き場所に置きます（Cloudflare版は`ModerationDurableObject`の`admin_state`の表、Vercel版は`mod:pause`）。
BANと一緒に読み（`ModerationStore.state`）、写しもBANと一緒に持ちます。

確かめるのは、部屋を作るとき、アセットを置くとき、Discordから戻ったときの3つです（`pausedNow`）。
どれも、BANを読み直すところと同じく、回数の上限を確かめたあとで、置き場所から読み直したものを見ます。
同じリクエストでBANも読み直すときは、読むのは1度です。
アセットを置くときは、置いてあるものと同じなら、止めずに置いてあると答えます。入った人が、手元の画像をまとめて確かめるためです。
トークンの更新、部屋に入ること、管理画面へのログインは止めません。

### 席に持たせるもの

席（`Seat`）には、送信元のIPアドレス（`address`）と、ログインした人のアカウント（`accountKey`、`discord:<ID>`）を持たせます。
どちらも部屋のサーバーの中だけのもので、ほかの参加者には送りません（`memberOf`は、ピアID・ユーザーID・役割だけを送ります）。

- IPアドレスは、部屋のサーバーがWebSocketを受けたときに`RoomEngine.accept`に渡し、`hello`で席に移します。Vercel版で中継する接続は、中継の`open`に載せて受け持つインスタンスへ送ります。
- Cloudflare版は、`accept`から`hello`までをメモリで持つので、そのあいだにDurable Objectが眠ると、その席にはIPアドレスが付きません。
- 部屋のアセットのトークンには、ログインした席のアカウントを`sub`として入れます。前の形のトークン（`sub`の無いもの）は、切れるまでの15分、Discordのアカウントでは確かめられません。

BANしたときは、人のいる部屋（一覧の人数が1以上）をすべて回り、`RoomEngine.expel`で当たる席を閉じます。
Vercel版で、部屋を受け持つのがほかのインスタンスのときは、受け持ちだけが聞くチャンネル（`r:<key>:own`）に`expel`を送ります。
受け持つインスタンスが無ければ、部屋にはだれもいません。

### 通報

部屋の席は、部屋のアセットのトークンで`POST /v1/rooms/:roomKey/reports`を呼んで通報します（`src/core/http/routes/reports.ts`）。見学も通報できます。
通報には、送信元のIPアドレス、トークンの`sub`から分かるDiscordのユーザーID、`uid`と`role`を、通報した人として付けて残します（`Report`）。虚偽の通報を見分けて、BANできるようにするためです。
置き場所は、Cloudflare版は`ModerationDurableObject`の`reports`の表（1件をJSONで）、Vercel版は`mod:reports`のHASHで、90日（`REPORT_MS`）と1000件（`MAX_REPORTS`）まで残します。
通報があると、知らせ（`report`、10分に1回まで）を送ります。知らせには通報した人のことは書きません。
管理画面は`GET /admin/api/reports`で読み、`PUT /admin/api/reports/:id`で状態（`open`・`done`・`dismissed`）を変えます。変えた人と時刻を通報に残し、管理の記録にも`report <状態> <id>`を書きます。

### 記録

ログイン、部屋を作った、新しく置いたアセット、回数の上限を超えた送信元、BANで断った送信元、管理画面での操作を、`ModerationStore.note`で残します。
書くのは答えを返したあと（Cloudflare版は`waitUntil`、Vercel版は`defer`）で、失敗してもログに出すだけです。
上限を超えた送信元とBANで断った送信元は、何度も来るので、インスタンスごとに、送信元（と上限）ごとに1分に1回だけ残します（`noteOnce`）。
回数の上限は、どちらの部屋のサーバーも`notingLimits`で包んでいるので、部屋のアセットを読む回数（置き場所の側で数えるもの）も残ります。
記録は、7日（`ACTIVITY_MS`）と2000件（`MAX_ACTIVITY`）のどちらかを超えたものから消します。
運営する人の操作（`isOperatorStep`：`admin`のうち、断られた試みのほか）は、別の置き場所（Cloudflare版は`operator_activity`の表、Vercel版は`mod:operator-activity`）に、90日（`OPERATOR_ACTIVITY_MS`）と1000件（`MAX_OPERATOR_ACTIVITY`）まで残します。ほかの記録がどれだけ増えても、運営する人の操作が押し出されないようにするためです。断られた試みは、だれでもいくらでも起こせるので、こちらには入れません。読むときは両方を合わせ、新しい順に並べます。

### 知らせ

`ADMIN_WEBHOOK_URL`があるときは、回数の上限を超えた、BANで断った、管理画面で断った、管理画面にログインした、を書くときに、DiscordのWebhookへ知らせます（`src/core/moderation/alerts.ts`）。
同じ種類の知らせは、すべてのインスタンスを合わせて10分（`ALERT_MS`）に1回にします。管理画面へのログインだけは、毎回送ります。
送ってよいかは置き場所に尋ね（`ModerationStore.claimAlert`）、Cloudflare版は`ModerationDurableObject`の`alerts`の表で、Vercel版は`mod:alert:<種類>`を`NX`と`PX`で置けたかで決めます。
知らせは答えを返したあとに送り、失敗してもログに出すだけです。
知らせには何があったかだけを書き、IPアドレスや参加者のアカウントは送りません（管理画面へのログインには、運営する人の表示名を書きます）。`allowed_mentions`を空にして、だれにもメンションしません。

置き場所の使用量は、`ADMIN_STORAGE_ALERT_GB`があるときだけ、1日1回数えます（`src/core/moderation/storage.ts`の`checkStorage`）。Cloudflare版は`wrangler.jsonc`の`triggers.crons`から`scheduled`が、Vercel版は`/internal/sweep`が掃除のあとに呼びます。`AssetBackend.inventory`を最後のページまで（`MAX_STORAGE_PAGES`まで）読んで足し、結果を置き場所に残します（Cloudflare版は`admin_state`の`storage_*`、Vercel版は`mod:storage`）。超えていれば知らせ、同じ知らせは20時間（`STORAGE_ALERT_MS`）に1回にします。

### 管理画面の画面

概要の数とグラフは、管理画面のAPI（部屋、記録、BAN）から、ブラウザの中で数えます。サーバーに集計のAPIはありません。
アップロードの一覧は、置き場所のすべての部屋のアセットを1ページずつ読みます（`AssetBackend.inventory`）。Cloudflare版はR2の`rooms/`の下を`list`で、Vercel版はRedisの部屋ごとのアセットの索引を`SCAN`で読みます。ブラウザは50ページまで読み、残りがあればそう出します。
置いた人は、記録の「アセットを置いた」の中身（`<種類> <大きさ> <SHA-256>`）と部屋の鍵で、ブラウザが突き合わせます。
中身を見るときは、`X-Admin-Request`を付けて読みます。画像は`data:`のURLから`img`で、音声はblobのURLから`audio`で出します（ページのCSPは`img-src`に`data:`、`media-src`に`blob:`を許します）。画像を`blob:`で出さないのは、`blob:`のURLが管理画面と同じオリジンを持つためです。SVGを別のタブで開くと、そのスクリプトが運営する人のログインで動いてしまいます。中身を返すAPIは`Content-Security-Policy: default-src 'none'; sandbox`を付け、直に開かれても何も動かないようにします。
中身を返すたびに、管理の記録に`view asset <SHA-256>`を部屋の鍵と運営する人のアカウント付きで残します。部屋に置かれたものはその卓のためのものなので、運営する人が何を見たかを、ほかの運営する人が確かめられるようにするためです。
「消して二度と置かせない」は、一覧で同じSHA-256が見つかった部屋の鍵を送ります。部屋のサーバーは、先に`blocked/<SHA-256>`の印を置いてから、それぞれの部屋から消します。印を先に置くのは、消すあいだに置き直されないようにするためです。消せなかった部屋は、ログに出して数を返します。
アカウントの削除は、本人が消すときと同じ`AccountPort.erase`を呼びます。
設定の画面に出すものは`GET /admin/api/settings`が決め、秘密の値は入っているかどうかだけを返します。
BANの「BAN中」は、ブラウザが範囲を読んで確かめます（`parseAddress`は部屋のサーバーの`address.ts`と同じ読みかた）。
部屋をまとめて削除するのも、BANと一緒に部屋を削除するのも、部屋を1つずつ削除するAPIを順に呼びます。
CSVは、表計算ソフトで数式として動かないよう、`=`・`+`・`-`・`@`などで始まるセルの頭に`'`を付けます。

### 手元で確かめる

手元の部屋のサーバーでも、管理画面を開いてBANを試せます。
`ADMIN_DISCORD_IDS`の書きかたと立てかたは、[部屋のサーバーの設定](https://xelltis.github.io/udonarium_axe_backend/server/configuration)の「手元で動かす」にあります。

- Discordでログインするには、DiscordのアプリのRedirectsに`http://localhost:8787/v1/login/discord/callback`と`http://localhost:8787/admin/login/callback`（Vercel版は`3000`）を足します。
- パスキーは`localhost`でも使えます（HTTPSでなくてよい）。手元のcookieは`__Host-`の付かない`axe-admin`です。
- パスキーの流れは、ChromiumのDevToolsの「WebAuthn」で仮の認証器を足すと、端末が無くても試せます。
- 手元からの接続は、どれも送信元が`127.0.0.1`などになります。IPアドレスでBANすると手元のタブがすべて止まるので、ふだんはDiscordのIDでBANして試します。管理画面はBANの対象にならないので、そこから解けます。
- 別のインスタンスでBANしたときの動きは、Vercel版なら手元で見られます。同じRedisを使う部屋のサーバーを`PORT`を替えて2つ立て、片方の管理画面でBANしてから、もう片方で部屋に入る・部屋を作るのが、すぐ止まることを確かめます。Cloudflare版の`npm run dev`はインスタンスが1つなので、これはテスト（`banElsewhere`）で確かめます。
